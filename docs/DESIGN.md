# 英単語暗記アプリ 設計書（実装仕様）

対象データ：`実践IELTS英単語3500_一覧.xlsx`（以下「元データ」）。覚える対象はこのデータだけで閉じている。使用者は1人（iPhoneメイン）。

この文書は実装の正。迷ったらここに従い、ここに書かれていない判断が必要になったら、実装前に使用者に確認する。

---

## 1. 設計原則

1. **知っている語に時間を使わない。** 1周目で既知語を高速で仕分けて外し、残りに時間を集中させる。
2. **状態は項目（単語・フレーズ）ごとに持つ。** 「周回期間」「SRS期間」をカレンダーで区切らない。各項目が条件を満たした時点で次の状態へ移る。
3. **回答ログが正、進捗は結果。** 進捗は回答ログを古い順に流し込めば必ず再現できる純粋な計算結果にする。ログは削除しない。
4. **毎日やることはアプリが決める。** 使用者は「始める」を押すだけ。
5. **崩れても戻れる。** 数日空いても復習が爆発しない上限と、復帰用の短時間モードを持つ。
6. **パラメータは1か所に集約。** 初期値は仮。後から変える前提で `params.ts` に集める。
7. **学習エンジンは言語非依存。** 将来、韓国語の単語データにも同じエンジンを使う。英語固有の処理（つづりの揺れ、活用形）はアダプタに分離する。

---

## 2. 元データの実態（調査済み）

- シートは1枚（`全項目`）、4,029行、12列。結合セルなし。
- 列：`行番号` `範囲` `番号` `単語` `意味` `例文` `例文の日本語訳` `類義語` `対義語` `語の出典` `例文の出典` `類義語・対義語の出典`
- `番号` はすべて一意の文字列。

### 行の3種類

| 種類 | 件数 | 見分け方 | 内容 |
| --- | --- | --- | --- |
| 本編の単語 | 3,500 | `番号` が数字のみ、`語の出典` = `Quizlet` | 単語・意味あり。例文は2,500件にあり |
| 音声のみの単語 | 429 | `番号` が数字＋英小文字（`10a` `19b` など）、`語の出典` = `音声のみ` | 単語帳の音声で追加で読まれる語。直前の番号の語の後ろに並ぶ。例文は334件にあり |
| フレーズ | 100 | `範囲` = `3501〜3600`、`単語` と `意味` が空 | 英語の例文と日本語訳だけ。IELTSのライティング・スピーキング用の定型表現 |

### 各列の書式

- **意味**：`【品詞】意味1；意味2` の形。品詞が複数ある語は `【動】を確保する；【形】安全な；安定した` のように続く（261語）。品詞は `名 動 形 副 前 接 代 助 接頭`、および `前・副` `代・形` のような複合。
- **例文**：1項目につき例文は最大1つ。ただし2文からなる例文が8件ある（フレーズ3件を含む）。単語の例文には日本語訳がない（日本語訳があるのはフレーズ100件だけ）。
- **例文の出典**：`音声` `作成` `音声（一部欠落）` `音声（聞き取り誤りを修正）` `音声（修正・一部欠落）`。「一部欠落」を含む例文（25件）は文が不完全な可能性がある。
- **類義語・対義語**：`, `（カンマ＋空白）区切り。類義語2,170件、対義語326件。出典は `Quizlet` または `追加（WordNetで選定）`。
- **見出し語**：イギリス式つづり（`organisation` `economise`）。複数語の見出し語が13件（`traffic jam` `usher in` など）。
- **重複**：`being` が番号1と999の2回出てくる（意味も同じ）。他に重複はない。
- **例文中の見出し語**：2,767件はそのままの形で含まれる（単語の途中を含む部分一致での数。単語の区切りで一致するのは2,061件）。58件は規則変化形、9件は不規則変化形（`undertook` `stung` `spat` `shrank` `ground` `clung` `wrung` `ushered in` など）。

## 3. データ変換（Python）

### 3.1 リポジトリ上の配置

```
data/raw/実践IELTS英単語3500_一覧.xlsx   # 元データ（gitignore）
data/overrides.json                       # 手修正（gitに入れてよい：番号と修正内容だけ）
data/out/items.json                       # 変換結果（gitignore）
data/out/report.md                        # 検証レポート（gitignore）
scripts/convert/                          # 変換スクリプト一式
  __main__.py   # コマンド（python -m scripts.convert）
  schema.py     # Item の型と元データの定数（列名・品詞・期待件数）
  parse.py      # 行の種類、意味、類義語・対義語、ID
  cloze.py      # 穴埋め位置
  merge.py      # 重複統合
  overrides.py  # 手修正の適用
  core.py       # 変換の流れと検証
  report.py     # report.md
tests/convert/                            # pytest（架空データのみ）
requirements.txt                          # Python の依存（バージョン固定）
```

**元データと変換結果はgitに入れない。** 市販の単語帳から作ったデータなので、公開リポジトリに置くと著作権の問題になりうる。アプリ本体のリポジトリは公開でもよい状態を保つ。

### 3.2 出力スキーマ（`items.json`）

TypeScript側の型と完全に一致させる（`app/src/data/types.ts` と `scripts/convert/schema.py` を対応させる）。

```ts
type Item = {
  id: string;                 // "ielts-0001", "ielts-0010a", "ielts-3501"。番号から作る安定ID
  kind: 'word' | 'phrase';
  origin: 'quizlet' | 'audio-only' | 'phrase';
  sourceNos: string[];        // 元データの番号。重複統合した語は複数（being → ["1","999"]）
  order: number;              // 元データの並び順（0始まり）。出題順・ブロック分けに使う
  block: number;              // 100件ごとのブロック番号（order から計算）

  // kind = 'word' のみ
  headword?: string;
  meanings?: { pos: string; text: string }[];  // 【動】を確保する；【形】安全な → [{pos:"動",text:"を確保する"},{pos:"形",text:"安全な"},...]
  meaningRaw?: string;        // 元の文字列（表示用）
  synonyms: string[];
  antonyms: string[];
  relationSource?: 'quizlet' | 'wordnet';

  // 例文（word は任意、phrase は必須）
  example?: {
    en: string;
    ja?: string;              // phrase のみ存在
    source: string;           // 元の「例文の出典」
    incomplete: boolean;      // 「一部欠落」を含むなら true
    cloze?: { start: number; length: number; form: string };  // 例文中の見出し語（変化形）の位置。form は例文中の実際の文字列（大文字もそのまま）。見つからなければ undefined
  };
};
```

### 3.3 変換の処理

1. `pandas.read_excel(dtype=str)` で読み込む。列名は上記の12列を前提にし、違えば即エラーで止める。
2. 行の種類を判定（2章の表のとおり）。
3. 意味を `【…】` ごとに分割し、各品詞グループを `；` で分割して `meanings` を作る。先頭の要素を代表の意味とする。
4. 類義語・対義語を `,` で分割し、前後の空白を除く。空なら空配列。
5. `being` のような重複は、小文字化した見出し語をキーに1件へ統合する（`sourceNos` に両方の番号、`order` は先に出た方）。統合した語の一覧をレポートに出す。
6. **穴埋め位置の特定**：例文中で見出し語またはその変化形を探す。
   - 大文字小文字を無視した単語境界一致 → 見つかればそれ。
   - なければ変化形を作って探す。変化形は `lemminflect` の全変化形（不規則変化を含む）に、自前の規則変化（-s/-es/-ed/-ing/-er/-est、y→ies/ied、e の脱落、子音を重ねる形と重ねない形の両方）を足したもの。`lemminflect` は `leaped` `enrolled`（英式の子音重ね）`regimens` を作らないため補う。
   - 複数語の見出し語は、先頭の語を変化させた形（`usher in` → `ushered in`）と最後の語を変化させた形（`humpback whale` → `humpback whales`）の両方を探す。
   - どの段階でもハイフンの有無は区別しない（`cleanup` ↔ `clean-up`、`delayering` ↔ `de-layering`）。
   - 一致が複数あれば、例文中で最も前にあるもの（同じ位置なら長い方）。
   - 接頭辞の見出し語（`pseudo-`）は探さない。
   - それでも見つからなければ `cloze` なしにして、レポートに出す（実データでは `ox`→`oxen` と `pseudo-` の2件。必要なら overrides で直す）。
   - `incomplete: true` の例文は穴埋めに使わない（`cloze` を付けない）。
7. `data/overrides.json`（番号 → 上書きするフィールド）を最後に適用する。手修正は元データではなくここに書くので、変換を何度やり直しても消えない。
   - キーは元データの番号（統合した語はどちらの番号でもよい）。先頭が `_` のキーはメモとして無視する。
   - 値は上書きする Item のフィールド。`null` はフィールドを消す。`id` `kind` `origin` `sourceNos` `order` `block` は上書きできない。
   - `example` は中身のキーごとに上書きする。`example.cloze` は文字列で書くと例文中でその文字列を探して位置を入れる（例：`{"1965": {"example": {"cloze": "oxen"}}}`）。
   - `meaningRaw` だけ書いたら `meanings` を作り直す。word の例文を変えて `cloze` を書かなければ穴埋め位置を探し直す。
8. 検証してレポートを出す（下記）。エラーがあれば終了コード1で、`items.json` は出力しない（古いものがあれば消す）。`report.md` は常に出す。

### 3.4 自動検証（`report.md` に出す）

- 件数：行の種類ごとの件数、統合後の総件数（期待値：単語3,928＋フレーズ100＝4,028）
- 必須欠け：word で意味が空、phrase で例文または日本語訳が空
- 見出し語に日本語・全角記号が混ざっている
- 意味が品詞タグで始まっていない、または未知の品詞タグ
- 穴埋め位置が見つからなかった例文の一覧
- 「一部欠落」の例文の一覧
- 統合した重複語の一覧
- 2文以上に見える例文の一覧（警告）
- 類義語・対義語と出典の食い違い（警告）、未知の出典（エラー）
- `cloze` の位置が例文と合わない（エラー。overrides の書き間違いを拾う）
- overrides の番号やフィールドの誤り（エラー）
- 参考：変化形で穴埋め位置を決めた例文（語形が変わるものは一覧、語尾が付いただけのものは件数）

エラーと警告の区別：件数・必須欠け・書式の誤りなど、そのまま取り込むと壊れるものがエラー。穴埋めなし・一部欠落・重複統合など、目で確認すればよいものが警告。

### 3.5 テスト

`pytest` で、少なくとも次をテストする：意味の分割（複数品詞を含む）、類義語の分割、行の種類判定、穴埋め位置（規則変化・不規則変化・複数語の先頭と最後・ハイフン）、重複統合、overrides の適用。テストのデータは架空のものだけを使う。

## 4. 項目の状態遷移

| 状態 | 入る条件 | 出る条件 |
| --- | --- | --- |
| `new`（未着手） | 取り込み時 | 仕分けで回答した |
| `known`（既知） | 仕分けで分類A | すぐ `srs` へ（Easy 1回分の履歴で入る）。後日の抜き打ち確認で不正解なら `cycle_waiting` へ戻る |
| `cycle_waiting`（周回の待機列） | 仕分けで分類B・C、または抜き打ちで不正解 | アクティブ枠に空きができた |
| `cycle_active`（周回中） | 待機列から補充された | 別々の日に2回連続正解 → `srs`／5ラウンド経過 → `srs`（苦手フラグ） |
| `srs`（SRS学習中） | 周回の卒業・救済、または既知 | なし（定着は `srs` の中の派生状態） |

「定着」は保存する状態ではなく、`srs` の項目について安定度から毎回計算する派生値（7章）。

## 5. 周回フェーズ

### 5.1 1周目：仕分け

目的は覚えることではなく、知っている語を早く外すこと。

- 出題順は `order` 順に100件ずつのブロック（`block`）。ブロック内はシャッフル。ブロックを途中でやめてもよく、再開時は残りから。（統合後の並びをそのまま区切るので、ブロック39は単語28件＋フレーズ72件になる。）
- **word の画面**：見出し語のみ（品詞も出さない）。右スワイプ＝知ってる、左スワイプ＝知らない。
- **phrase の画面**：日本語訳を表示し、「英語で言える」＝右、「言えない」＝左。（IELTSで使うための表現なので、日→英の方向で判定する。）
- 「知ってる」の後、代表の意味（phrase は英文）を5秒表示して自動で次へ（カードをタップすればすぐ次へ）。その間に「違った」をタップすると訂正あり（下の表の分類B）になり、「知らない」と同じ詳細表示に切り替える。表示中にアプリを閉じたら「知ってる」（訂正なし）として保存する。
- 「知らない」の後は、意味・例文・類義語・対義語（phrase は英文と訳）を表示し、タップで次へ（最初のインプットを兼ねる）。
- 表示からスワイプまでの時間（ms）を記録する（指を離した時点まで。カードが飛ぶ演出の時間は含めない）。
- 画面上部の「戻る」で直前の回答を取り消せる（ログに `undone: true` を付け、その項目をもう一度出す）。

| 分類 | 条件 | 行き先 |
| --- | --- | --- |
| A | 知ってる＋即答基準以内（初期3秒）＋訂正なし | `known` → すぐ `srs` |
| B | 知ってる＋即答基準超、または訂正あり | `cycle_waiting`（連続正解1から開始） |
| C | 知らない | `cycle_waiting`（連続正解0から開始） |

**抜き打ち確認**：分類Aの項目のうち10%（初期値）を、仕分けの翌日以降に4択（phrase は自己採点）で出す。不正解なら `cycle_waiting` に戻し、SRSの状態は破棄する。抜き打ちの正答率が80%未満なら、設定画面で即答基準を下げるよう提案する。

### 5.2 2周目以降：アクティブ枠での周回

- **アクティブ枠**：同時に周回する項目数の上限（初期400）。`cycle_waiting` から `order` 順に補充する。
- **ラウンド**：アクティブ枠の全項目を1回ずつ出し終えるまでを1ラウンド。1日の周回量は枠の約1/3（各項目に約3日ごとに出会う）。
- **枠に入った直後の1回目**：テストせずインプットカード（意味・例文など）を見せる。
- **出題形式**：フラッシュカード。word は英→日（見出し語を見て思い出し、タップで意味表示、「わかった／わからなかった」）。phrase は日→英（訳を見て英文を思い出し、タップで英文表示）。
- **同じ日の再確認**：「わからなかった」項目はそのセッションの最後にもう一度出す。同じ日の2回目以降の回答は連続正解に数えない。
- **卒業**：別々の日に2回連続正解 → `srs`。間違えたら連続正解を0に戻す。
- **救済**：5ラウンドで卒業できなければ、苦手フラグ付きで `srs` へ。
- 卒業・救済で空いた枠は即座に補充。待機列とアクティブ枠が空になれば周回フェーズ終了。

## 6. SRSフェーズ

### 6.1 FSRS

- ライブラリ：`ts-fsrs`（FSRS v6）。`fsrs(generatorParameters({...}))`、`createEmptyCard`、`scheduler.next(card, date, rating)`、`get_retrievability` を使う。バージョンは最新の安定版を確認して固定する。
- `request_retention`：0.90
- `enable_fuzz`：true
- `maximum_interval`：通常は既定。試験日の6週間前からは「試験日までの日数」に制限（7章）。
- パラメータ最適化は将来対応。ログはそのために全項目保存しておく。

### 6.2 周回からSRSへの引き継ぎ（リプレイ）

SRSへ移る瞬間に、その項目の回答ログを古い順に `scheduler.next` へ流し込んで初期カードを作る。

| 回答 | FSRSの評価 |
| --- | --- |
| 仕分けで分類A | Easy |
| 仕分けで分類B | Hard |
| 仕分けで分類C | Again |
| 周回で「わかった」 | Good |
| 周回で「わからなかった」 | Again |
| 同じ日の2回目以降 | 流し込まない |

### 6.3 評価の付け方

画面のボタンは「わからない」「わかった」の2つ。

| 状況 | 評価 |
| --- | --- |
| 自己採点で「わからない」／選択・入力で不正解 | Again |
| 正解だが回答8秒以上／ヒント使用／入力で1文字違い | Hard |
| 普通に正解 | Good |
| 自己採点で「わかった」を長押し | Easy |

Easyは自動では付けない。FSRSに入れるのは1日（4時区切り）の最初の回答だけ。

### 6.4 出題形式の段階化（word）

安定度（stability、日）で形式を決める。

| 段階 | 安定度 | 形式 |
| --- | --- | --- |
| 1 | 3日未満 | 英→日 4択 |
| 2 | 3〜10日 | 英→日 フラッシュカード（自己採点） |
| 3 | 10〜30日 | 日→英 入力（頭文字ヒントボタンあり） |
| 4 | 30日以上 | 例文の穴埋め入力（`cloze` がある項目のみ。なければ段階3） |
| 補助 | 10日以上 | 音声→意味の4択、類義語・対義語の選択。段階3以上の出題の約2割に混ぜる。データがない項目には出さない |

- **形式が上がった直後の失敗**：初めてその形式で出した回の失敗は Again ではなく Hard とし、次回は一段下の形式に戻す。
- **phrase**：段階1〜2は日→英フラッシュカード（自己採点）、段階3以上は日→英で英文を入力し、正解と並べて自己採点（「言えた」「言えなかった」）。完全一致判定はしない。

### 6.5 4択の作り方

- 誤答は同じ品詞の他の word の代表の意味から3つ。
- その項目の類義語・対義語に当たる語の意味は選択肢に入れない。
- 文字数が正解と大きく違うものは避ける。
- 誤答を選んだら、選んだ選択肢の項目IDをログに残す（混同ペア検出に使う）。

### 6.6 入力問題の判定（英語アダプタ）

- 大文字小文字・前後の空白を無視。
- 編集距離1は正解（評価 Hard）。
- イギリス式／アメリカ式のつづりの揺れを許容する（`-ise/-ize` `-isation/-ization` `-our/-or` `-re/-er` `-ll-/-l-` など）。正規化関数を英語アダプタに置き、テストを書く。
- 入力がその項目の類義語だった場合は不正解にせず「それは類義語。別の語は？」と出して再入力させる。
- 穴埋めの正解は `cloze.form`（例文中の実際の形）。

### 6.7 1回の回答の流れ

1. 期限切れ・期限当日の項目を、思い出せる確率の低い順に並べる。
2. 形式を決めて出題。
3. 回答と回答時間から評価を決める。
4. `scheduler.next` で次の期限を計算し、ログを保存して進捗を更新。
5. Again の項目はセッションの最後にもう一度（FSRSには入れない）。

## 7. 定着の判定と試験日対応

| レベル | 条件 |
| --- | --- |
| 定着（受容） | `srs` かつ安定度21日以上 |
| 定着（産出） | 安定度30日以上、かつ直近の段階3・4（phrase は段階3）で正解 |

- 復習で間違えて安定度が下がれば、自動的に定着から外れる（降格）。週ごとの降格数を統計に出す。
- **定着率**：定着（受容）の項目数 ÷ 総項目数。メインの進捗。
- **期待語彙数**：全項目の「今思い出せる確率」の合計。`new` は0、周回中は直近ラウンドの正答状況から仮の値（正解なら0.6、不正解なら0.2。`params.ts` に置く）。
- **試験日の期待語彙数**：全項目の「試験日に思い出せる確率」の合計。
- **試験日対応**：試験日（設定）の6週間前から最大間隔を試験日までの日数に制限。4週間前からは、試験日に思い出せる確率が0.85未満の項目を確率の低い順に前倒しで復習に入れる。試験日が未設定なら何もしない。

## 8. 苦手語（リーチ）

- 条件：SRSで忘却（Again）4回以上、または周回からの救済。
- 次の出題時、テストの前に「じっくり確認カード」（全データ＋自分メモ欄）を出す。メモは進捗側に保存し、以後の回答後表示に出す。
- しばらく（次の正解まで）は段階1の形式で出す。
- **混同ペア**：4択で同じ2項目の取り違えが2回起きたら登録し、次にどちらかが出るとき2語の比較カードを先に出す。
- 苦手語が全体の5%を超えたら、ホームでアクティブ枠を1割減らすことを提案する。

## 9. セッション設計

- 1日の区切りは午前4時（端末のタイムゾーン、実質JST）。時刻はテストのため注入可能な `clock` から取る。
- **時間予算**（初期15分）の中で、上から順に詰める。
  1. SRSの期限切れ・当日分（思い出せる確率の低い順、1日上限150件。抜き打ち確認もここに含める）
  2. 周回のアクティブ枠（今日のラウンド分）
  3. 1周目の仕分け（未着手がある間）
- 1問あたりの時間は形式ごとの平均（直近のログから）で見積もる。ログがない間の仮値：仕分け3秒、周回5秒、4択6秒、フラッシュ7秒、入力12秒。
- セッションは約20問の「ミニセット」単位。ミニセットごとに保存・同期するので、どこでやめてもよい。
- **短時間モード**：期限切れのSRSから思い出せる確率が低い順に20問。
- **自動ブレーキ**：翌日の期限件数の予測が上限を超えそうなら、アクティブ枠の補充を止める。
- **数日空いた後**：期限切れが上限を超えていれば、思い出せる確率の低い順に上限分だけ出し、残りは翌日以降へ。
- **ペース見込み**：試験日があれば、直近7日の卒業・救済ペースから周回フェーズの完了見込み日を出し、試験日の8週間前より遅ければ枠か時間予算を増やすよう提案する。

## 10. 継続の仕組み

- 起動したらすぐ「始める」が押せる（オフラインで動く、読み込み待ちなし）。ボタンは画面の下半分。
- **ストリーク**：1日に短時間モード相当（20問）以上で学習日。週1回の「お休みチケット」を自動付与。「今月の学習日数」も並べて表示。
- **進捗表示**：周回フェーズ中は「待機中の知らない項目数」を最も大きく表示。4色バー（未着手／周回中／SRS／定着）。期待語彙数の週ごとの推移。ブロック完了や定着500件ごとに短い完了表示。
- **離脱からの復帰**：3日以上空いたら「おかえり」画面で短時間モードを勧める。
- **週の振り返り**：日曜に学習日数・卒業数・定着数・降格数・試験日の見込み。
- **通知**（後半のステップ）：朝に「今日は復習42件＋周回90件、約14分」。夜は、その日まだ何もしていない場合だけ短時間モードへ誘導。

## 12. データ保存

### 12.1 端末（正）

IndexedDB（Dexie）に次を持つ。

- `items`：取り込んだ `items.json`
- `progress`：項目ごとの進捗（下の型）
- `logs`：回答ログ
- `meta`：設定、日ごとの集計、同期状態

```ts
type ReviewLog = {
  id: string;                 // ULID
  itemId: string;
  at: number;                 // epoch ms
  day: string;                // 'YYYY-MM-DD'（4時区切り）
  phase: 'sort' | 'cycle' | 'srs' | 'spot' | 'drill';
  format: 'swipe' | 'input' | 'flash' | 'choice4' | 'typeEn' | 'cloze' | 'audio' | 'relation' | 'phraseType' | 'compare';
  outcome: 'known' | 'unknown' | 'correct' | 'wrong' | 'shown';
  grade?: 1 | 2 | 3 | 4;      // FSRSに渡した評価
  ms: number;                 // 回答時間
  fsrsEligible: boolean;      // その日最初の回答か
  undone: boolean;
  meta?: { corrected?: boolean; chosenItemId?: string; hintUsed?: boolean; typo?: boolean; formatPromoted?: boolean };
};

type Progress = {
  itemId: string;
  state: 'new' | 'known' | 'cycle_waiting' | 'cycle_active' | 'srs';
  sortClass?: 'A' | 'B' | 'C';
  cycle?: { rounds: number; streak: number; lastCorrectDay?: string; lastSeenDay?: string; inputShown: boolean };
  card?: SerializedCard;      // ts-fsrs の Card（Date は epoch ms で保存）
  formatStage?: number;
  flags: { leech?: boolean; rescued?: boolean; spotCheckPending?: boolean };
  memo?: string;
  confusions: string[];
  updatedAt: number;
};
```

**進捗のリセット**（使用者の要望で追加）：ログは消さず、その時点で有効なログすべてに `undone: true` と `meta.resetAt`（リセットした時刻）を付けてから進捗を作り直す。仕分けの出題順のシードも新しくする。設定画面で確認を1回はさんでから実行する。

**進捗はログからの純粋な畳み込みで作る**：`reduce(logs, initialProgress, items, params)`。進捗テーブルはその結果のキャッシュ。ルールやパラメータを変えたら全ログから作り直せること（テストで保証する）。

### 12.2 単語データの取り込み

`items.json` はアプリ本体（公開リポジトリ）に含めない。最初は設定画面の「単語データを取り込む」からファイルを選んで IndexedDB に入れる（MacからiPhoneへAirDropして「ファイル」から選ぶ）。同期の実装後は Firestore にも置き、新しい端末ではそこから取得する。

- 取り込み直すと単語データだけを入れ替え、ログは残したまま進捗をログから作り直す。
- 開発サーバー（`npm run dev`）でだけ、`data/out/items.json` をボタン1つで読み込める（本番ビルドには入らない）。

### 12.3 同期（Firestore）

無料枠は1日あたり読み取り5万件・書き込み2万件。1項目1ドキュメントにすると上限に当たるので、まとめて持つ。

```
users/{uid}/items/{chunkNo}          … items.json を500件ずつ
users/{uid}/progressChunks/{chunkNo} … 進捗を500件ずつ（変更のあったチャンクだけ書く）
users/{uid}/logBatches/{batchId}     … ミニセットごとのログ
users/{uid}/meta/settings
```

- 同期はミニセット終了時と起動時。起動時は最終同期以降に更新されたものだけ読む。
- 競合は項目ごとに `updatedAt` が新しい方。ログは追記のみなので競合しない。
- セキュリティルールで自分の `uid` 以下だけ読み書き可。
- 認証は Firebase Auth の Google ログイン。

### 12.4 バックアップ

設定画面から進捗・ログ・設定をJSONで書き出し・読み込み。同期の実装前から使えるようにする。

## 15. 開発ステップ

各ステップの最後に「完了の目安」を満たしたことを確認してから次へ進む。

1. **データ変換**：`scripts/convert/`、pytest、`items.json` と `report.md`。
   完了の目安：検証エラー0（警告は一覧で使用者が確認）、件数が期待値どおり。

6. **同期**：Firebase Auth、Firestore、バックアップ読み込み。
